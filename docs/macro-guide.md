## 1. עקרונות העבודה (לקרוא פעם אחת, לזכור לתמיד)

**בונים בפרוסות אנכיות (Vertical Slices).** לא בונים קודם את כל הדאטהבייס, אחר כך את כל המסכים. במקום זה — לוקחים מודול אחד ובונים אותו מקצה לקצה: הרשאות (RLS) ← מסך רשימה ← טופס ← לוגיקה עסקית ← בדיקה. רק כשהוא עובד שלם — עוברים למודול הבא.

**סדר התלויות = סדר הבנייה.** מודול שמסתמך על מודול אחר נבנה אחריו. הטבלה בסעיף 3 מראה בדיוק מה תלוי במה.

**היררכיית מקורות אמת (כשיש סתירה — מי קובע):**
1. **סכמת ה-DB ב-Supabase** — החוזה הטכני הקשיח. שמות עמודות, טיפוסים ו-constraints הם עובדה.
2. **האפיון (הדוח המאושר)** — מקור האמת ללוגיקה העסקית, להרשאות ולנוסחאות. **גובר על המסכים ועל מדריך המודולים.**
3. **המוקאפים (צילומי המסך)** — שפת עיצוב ופריסה. ממחישים כוונה, לא מחייבים בפרטים.
4. **מדריך המודולים** — מתכון לסדר העבודה. הכי נמוך בסולם.

**הערה טכנולוגית:** אנחנו על **Vite** (לא Next.js), JavaScript (לא TypeScript), Tailwind 4, shadcn/ui, Supabase. כל הקוד וההערות בעברית. ה-alias `@/` מצביע על `src/`.

## 4. מפת העבודה המקבילה (מי עובד על מה באותו זמן)

ישי:    [0]  [-- 1 --]  [---- 4 ----][- 5 -]            [9][-- 10 --]

**מה זה אומר בפועל:**
- **שבועות 2–3:** ישי בונה את מודול 1 (הרשאות), עמית בונה במקביל את מודול 2 (לקוחות). שניהם נשענים על התשתית של מודול 0 שכבר קיימת.

- אמצע הסמסטר (שבועות 6–8) — שניכם מתכנסים יחד למודול 6 (פרויקטים), כי הוא מחבר בין הצעות מחיר, דיילות ולוגיסטיקה. זו נקודת אינטגרציה גדולה.

## 7. שיטת העבודה ב-Git (החלק הכי חשוב לשיתוף פעולה) 🔑

המטרה: שניכם תעבדו במקביל בלי לדרוס אחד את השני, ובלי שהקוד "יישבר" אצל אף אחד.

### 7.1 מבנה ה-Branches

- **`main`** — הגרסה ה"רשמית" והיציבה. נוגעים בה רק באבני דרך. **מוגן** (לא דוחפים אליה ישירות).
- **`dev`** — ענף האינטגרציה. לכאן מתנקזת העבודה של שניכם דרך PR. **מוגן** גם הוא.
- **branch אישי לכל מודול** — כאן עובדים בפועל. שם בפורמט: `שם/מודול`, למשל:
  - `ishay/module-1-permissions`
  - `amit/module-2-customers`

### 7.2 הגדרה חד-פעמית (לעשות פעם אחת)

ישי (בעל הריפו) יוצר את ה-branches ומגן עליהם:
```bash
# מתוך התיקייה המקומית, אחרי שהריפו מחובר ל-GitHub:
git branch dev          # יצירת ענף dev
git push -u origin dev  # העלאתו ל-GitHub
```
ואז ב-GitHub: **Settings → Branches → Add rule** ל-`main` ול-`dev` — לסמן "Require a pull request before merging".
עמית עושה **clone** לריפו: `git clone <כתובת-הריפו>` ויוצר לעצמו `.env.local` משלו (ראו 7.5).

### 7.3 הזרימה היומית (כל אחד, בכל יום עבודה)

```bash
# 1. לפני שמתחילים — להתעדכן בגרסה האחרונה של dev
git checkout dev
git pull origin dev

# 2. ליצור/לעבור ל-branch האישי של המודול
git checkout -b ishay/module-1-permissions   # בפעם הראשונה
# (בפעמים הבאות: git checkout ishay/module-1-permissions)

# 3. ...עובדים, כותבים קוד...

# 4. בסוף יום עבודה / סיום משימה — שומרים ודוחפים
git add .
git commit -m "מודול 1: מסך רשימת משתמשים + טופס הוספה"
git push origin ishay/module-1-permissions
```

### 7.4 ה-Merge (כשמודול/חלק גמור)

**עושים merge דרך Pull Request ב-GitHub, לא בשורת הפקודה** — זה בטוח יותר למתחילים ומאפשר לשותף לעבור על הקוד.

1. נכנסים ל-GitHub → הריפו → לשונית **Pull requests** → **New pull request**.
2. בוחרים: `base: dev` ← `compare: ishay/module-1-permissions`.
3. כותבים תיאור קצר של מה נעשה, ולוחצים **Create pull request**.
4. **השותף השני** נכנס, עובר על השינויים, ומאשר (**Merge pull request**).
5. עכשיו `dev` מעודכן. שניכם עושים `git checkout dev` ואז `git pull origin dev` כדי לקבל את העדכון.

מ-`dev` ל-`main` עושים merge רק באבני דרך (M1–M5), באותה שיטת PR.

### 7.5 כללי ברזל למניעת אסונות

- 🔒 **לעולם לא לדחוף `.env.local`** ל-Git. הוא חייב להופיע ב-`.gitignore` (הוא כבר שם). לכל אחד מכם יש עותק `.env.local` מקומי משלו עם אותם מפתחות Supabase.
- 🗄️ **אתם חולקים פרויקט Supabase אחד** (אותו URL ואותם מפתחות). זה אומר שה-DB משותף ביניכם עוד לפני שהקוד מתמזג — שינוי שאחד עושה בטבלאות משפיע על השני. תאמו שינויי סכמה!
- 🧩 **כל אחד עובד ברוב הזמן בתיקיית המודול שלו** תחת `src/modules/`. ככה כמעט ולא נוצרים conflicts.
- 🔄 **למשוך `dev` כל בוקר** לפני שמתחילים — ככה לא נוצר פער ענק שקשה למזג.
- 💬 **commit קטן ותכוף** עדיף על commit ענק פעם בשבוע. כל commit עם הודעה ברורה בעברית.
- ⚠️ אם בזמן merge מופיע **conflict** — לא נבהלים. עוצרים, שולחים צילום מסך, ופותרים יחד.

## 8. איך בנויים מדריכי המיקרו

לכל מודול יש מדריך מיקרו נפרד (קובץ `.md` משלו). הוא לא ערימת קוד — הוא **רשימת צעדים ממוספרת**, ולכל צעד:
- מה עושים (במשפט פשוט),
- **נקודת עצירה** — מה אמור לקרות / מה לבדוק,
- מי אחראי (אם המודול משותף).

את **הקוד עצמו כותבים יחד בשידור חי** עם Claude, צעד-צעד, כמו שעבדנו על התשתית. המדריך הוא המפה; הקוד נכתב כשמגיעים לכל תחנה.

**הסדר:** מייצרים מדריך מיקרו לכל שלב *כשמגיעים אליו* — לא את כולם מראש — כי הפרטים מתחדדים תוך כדי, וכך לא מציפים את עצמנו. המדריך הראשון (מודול 1) כבר מוכן.

## 10. כללי התנהלות ל-AI (Claude) — Rules of Engagement

1. **שאל שאלות הבהרה לפני עבודה** כשמשהו לא חד-משמעי (קוד, DB, מבנה קבצים) — אל תניח.
2. **Plan Mode:** לתכנן ולקבל אישור לפני ביצוע; במצב תכנון לא נוגעים בקבצים (מלבד קובץ התוכנית).
3. **הערות בעברית, "why-first":** להסביר את הכוונה האדריכלית ואת הטיפול במקרי-קצה — לא לתאר תחביר. לשמור על צפיפות ההערות של הקוד הסובב (לא להעמיס על קוד שכבר ברור).
4. **לצטט קובץ+שורה**, לא לסמוך על הזיכרון.
5. **לא לשכתב/למחוק טבלאות קיימות.** שינויי DB רק דרך **migration בעל שם** עם כותרת "why" בעברית.
6. **לעולם לא לקמט סודות** (`.env.local`, סיסמאות) ל-Git.
7. **תיעוד וסנכרון (חובה):** בסוף כל צעד — לתעד ב-`CLAUDE_CODE_LOG.md` (נרטיב/למה) + שורה מתוארכת ב-`CHANGELOG.md`, וליישר כל מסמך שנסתר מהמציאות. חלוקת האחריות בין הקבצים: ראו §12.
8. **לוודא בפועל (verify):** להריץ את האפליקציה/בדיקות ולראות שהשינוי עובד — לא להסתפק בהנחה.

- **מתעדים רק DDL / פונקציות / טריגרים / RLS.** לא מתעדים INSERT/UPDATE/DELETE של בדיקה. Seed (roles/modules) הוא היוצא-מן-הכלל המותר (הוא מגדיר את מטריצת ההרשאות).
- **כל שינוי DB = migration בעל שם** עם כותרת "why" בעברית.
- **מי מתעד מה (בלי כפילות):** `CLAUDE_CODE_LOG.md` = נרטיב/למה/החלטות/tech-debt · `CHANGELOG.md` = שורות מתוארכות (`סוג DB/קוד · מי · מה · מודולים מושפעים`) · מדריך זה = כללים + מצביע-סטטוס בלבד.

### יומן DB — מודול 1 (נכון ל-03/07/2026)
- **פונקציות:** `current_user_role_id() → int` · SQL · STABLE · SECURITY DEFINER · `search_path=''` (לאחר הקשחה). מחזירה `role_id` של המשתמש המחובר (`auth.email()`) רק אם `status='active'`. עוקפת RLS ולכן חסינה מרקורסיה בתוך policies של `users`. הרשאת EXECUTE: `authenticated`/`postgres`/`service_role` בלבד (`anon`/PUBLIC הוסרו).
- **פונקציות נעילת חשבון (03/07):** `check_login_lock(text)` (מחזיר `locked_until` אם נעול; EXECUTE ל-`anon`+`authenticated`) · `register_failed_login(text)` (מונה כשלונות, נועל אחרי 5 ל-15 דק'; EXECUTE ל-`anon`+`authenticated`) · `reset_login_attempts()` (מאפס לפי `auth.email()`; EXECUTE ל-`authenticated` **בלבד**). כולן SECURITY DEFINER, `search_path=''`.
- **טבלאות (03/07):** `login_attempts` (`email` PK, `failed_count`, `locked_until`, `last_attempt_at`) — RLS-on **בלי policies**; גישה רק דרך 3 הפונקציות למעלה.
- **טריגרים:** אין. (במיוחד: אין `handle_new_user` המסנכרן `auth.users`→`public.users`; משתמשים נוצרים דרך seed / מסך המנכ"ל.)
- **RLS:** `roles`/`modules`/`permissions` — SELECT לכל authenticated; `permissions` כתיבה למנכ"ל בלבד. `users` — SELECT self-או-מנכ"ל · `users_update_self` (UPDATE, מקפיא `role_id`+`status`) · write למנכ"ל. **11 טבלאות מודולים עתידיים:** RLS מופעל, אפס policies = deny-all מכוון עד בניית המודול.
- **מיגרציות:** `…112703` soft-delete (frozen→inactive) · `…143254` users_update_self · `…143405` fix_recursion · `harden_current_user_role_id` (02/07) · `module1_login_attempts_lockout` + `module1_reset_login_attempts_revoke_anon` (נעילת חשבון, 03/07).
- **חוב DB פתוח:** `authenticated` עדיין יכול לקרוא לפונקציה כ-RPC (נדרש ל-RLS — מקובל) · Leaked-Password Protection כבוי (מודול 10) · `auth.email()` לא עטוף ב-`(select …)` ב-2 policies (אופטימיזציית initplan עתידית).
