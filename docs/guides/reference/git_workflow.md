# 🌿 רפרנס — Git ולולאת המודול (ברמת אפס-ניסיון)

> מקומו בהיררכיית האמת: הוראות תפעוליות בלבד.
> **מסמך רפרנס** — שיטת ה-Git הקנונית של הפרויקט. חוזרים אליו בכל פעם שהמכניקה מתערפלת.

## ① מה נשיג כאן

אתה מבין ומתרגל בפועל את שיטת העבודה ב-Git שהפרויקט משתמש בה, ואת "הלולאה" שכל מודול נבנה בה עם Claude — כדי שכשתתחיל מודול אמיתי לא תצטרך לחשוב על המכניקה, רק על התוכן.

## ② תנאי כניסה

- [ ] הריפו משוכפל (`git clone`) והאתר רץ מקומית (`npm run dev`).

## ③ חלוקת עבודה

| אתה | Claude |
|---|---|
| מריץ פקודות Git, פותח וממזג את ה-PR | מלווה, מסביר, בונה את השינוי |

## ④ החלק שלך — מבנה ה-Branches

- **`main`** — הגרסה הרשמית והיציבה. נוגעים בה רק באבני דרך (M1–M5). מוגן — אי אפשר לדחוף אליה ישירות.
- **`dev`** — ענף האינטגרציה. לכאן מתנקזת כל העבודה, דרך Pull Request. גם הוא מוגן.
- **ענף אישי לכל מודול** — כאן עובדים בפועל בכל יום. פורמט: `ishay/module-N-נושא`, למשל `ishay/module-2-customers`.

### הזרימה היומית
```bash
git checkout dev
git pull origin dev

git checkout -b ishay/module-2-customers   # בפעם הראשונה על מודול
# (בפעמים הבאות: git checkout ishay/module-2-customers)

# ...עובדים, Claude כותב קוד...

git add .
git commit -m "מודול 2: מסך רשימת לקוחות + טופס הוספה"
git push origin ishay/module-2-customers
```

### מיזוג (Merge) — דרך Pull Request, לא משורת הפקודה
1. GitHub → הריפו → **Pull requests** → **New pull request**.
2. `base: dev` ← `compare: ishay/module-2-customers`.
3. תיאור קצר → **Create pull request**.
4. **עבור בעצמך על ה-diff ב-PR** (טאב "Files changed") — זו הסקירה האחרונה לפני שהקוד נכנס ל-`dev`, לא טקס. **המתן שבדיקות ה-CI ירוקות**, ורק אז **Merge pull request**. ‏CI אדום = לא ממזגים, מתקנים קודם.
5. אחר כך: `git checkout dev && git pull origin dev` — כדי לקבל את העדכון מקומית.

> 💡 **למה בכלל PR כשעובדים לבד?** ה-PR הוא לא "בקשת אישור ממישהו" — הוא **שער ה-CI וההיסטוריה**: הבדיקות רצות עליו, ה-diff נקרא במרוכז לפני שהוא נכנס ל-`dev`, וכל שינוי מקבל רשומה מתועדת ב-GitHub. גם לבד — לא ממזגים משורת הפקודה.

> 🧩 **פרומפט לקלוד בדפדפן** (פתיחת PR — הדבק בתוסף הכרום כשאתה ב-GitHub; החלף את שם הענף בענף שלך):
> ```
> אני בריפו Reg-In ב-GitHub. פתח Pull Request חדש: base: dev ← compare: <שם-הענף-שלי>.
> כותרת קצרה בעברית שמתארת מה השתנה. צור את ה-PR והראה לי את סטטוס בדיקות ה-CI.
> אם ה-CI אדום — העתק לי את הודעת השגיאה המלאה; אל תמזג כלום בעצמך.
> ```

### כללי ברזל
- 🔒 לעולם לא דוחפים `.env.local` ל-Git.
- 🗄️ **כל שינוי סכמה עובר אך ורק דרך קובץ-מיגרציה בעל-שם** ב-`supabase/migrations/` — אף פעם לא SQL אד-הוק בסטודיו. זה מה ששומר על היסטוריית-DB שאפשר לשחזר ולקרוא (פרוטוקול DB ב-`CLAUDE.md`).
- 🧩 עובדים ברוב הזמן בתיקיית המודול (`src/modules/NN_name/`) — כך נמנעים conflicts גם בין ענפים של אותו מפתח.
- 🔄 מושכים `dev` לפני כל התחלת עבודה.
- 💬 commit קטן ותכוף, הודעה ברורה בעברית.
- ⚠️ conflict? לא נבהלים — עוצרים, מציגים את הקובץ המסומן ל-Claude, ופותרים איתו שורה-שורה. לא "לפתור מהר" בניחוש.
- 🔁 **מיזגת PR והמשכת לעבוד?** אל תערום commits חדשים על ענף שכבר מוזג — `git fetch origin` ואז ענף חדש מ-`dev` טרי (כלל ברזל 10).

## ⑤ החלק של Claude — תרגול PR

Claude מלווה אותך בשינוי-תרגול **זעיר ומוסכם מראש**: תיקון טקסט קטן ב-README הראשי. המטרה: לעבור פעם אחת על כל הזרימה (ענף → commit → push → PR → CI ירוק → merge → pull) לפני שעושים את זה עם קוד אמיתי.

## ⑦ בדיקת קבלה

- [ ] הענף התרגולי נוצר, ה-commit בוצע, וה-push עבר.
- [ ] PR נפתח ב-GitHub, ה-CI ירוק, וה-merge הצליח.
- [ ] `git checkout dev && git pull` מציג את השינוי שלך.

## ⑧ אם משהו השתבש

- **`git push` מציג "rejected"** — הענף המרוחק מכיל commits שאין לך; הרץ `git pull` ואז נסה שוב.
- **conflict בזמן pull/merge** — אל תלחץ שום דבר; פתח את הקובץ המסומן מול Claude ופתרו יחד (יש פרומפט מוכן ב[ספריית הפרומפטים המצביים](../prompt_library.md)).
- **PR לא מופיע ב-GitHub** — ודא שדחפת בהצלחה (`git push` בלי שגיאה) ושבחרת `base: dev` נכון.
