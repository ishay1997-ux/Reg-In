# 📚 ספריית הפרומפטים המצביים — REG-IN

> מקומו בהיררכיית האמת: הוראות תפעוליות בלבד.
> **מה יש כאן:** פרומפטים מוכנים להדבקה לסיטואציות שחוזרות על עצמן — תקלות, שינויים, שאלות. **מה אין כאן:** פרומפטי הפתיחה/המשך/סגירה של מודול — הם חיים בסעיף ⑥ של מדריך השלב שלך (כבר ממולאים פר-מודול). מתי מריצים רוטינות — [המפה ב-claude_routines.md](../claude_routines.md).
> **איך משתמשים:** מוצאים את הסיטואציה בטבלה → מעתיקים את הפרומפט → ממלאים את `[ישי/עמית]` ואת השורות עם `___` → מדביקים ל-Claude Code. טיפ: שגיאות מדביקים **במלואן**, לא מסכמים.

## <a name="p1"></a>P1 · האוניברסלי — "איפה עצרנו"
🕐 בכל חזרה לעבודה, כשלא זוכרים מה השלב.
```
אני [ישי/עמית]. קרא את CLAUDE.md ואת STATUS.md והמשך מאיפה שעצרנו במסלול שלי.
לפני שאתה עושה משהו — הסבר לי במילים פשוטות איפה אנחנו עומדים ומה השלב הבא.
```

## <a name="p2"></a>P2 · התחלת מדריך-שלב
🕐 בתחילת מדריך הקמה/התקנה (למדריכי מודול יש פרומפטים מדויקים ב-⑥ שלהם).
```
אני [ישי/עמית]. אנחנו בפרויקט REG-IN. קרא את CLAUDE.md, את STATUS.md ואת docs/guides/___/__________.md
ובצע את "החלק של Claude" בשלב הזה.
בסוף: עדכן את היומנים ואת STATUS.md לפי הפרוטוקול ב-CLAUDE.md,
והסבר לי במילים פשוטות מה לבדוק ואיך.
```

## <a name="p3"></a>P3 · חילוץ — "משהו השתבש"
🕐 כל תקלה: שגיאה במסך, פקודה שנכשלה, התנהגות מוזרה.
```
אני [ישי/עמית]. משהו השתבש. קרא את CLAUDE.md ואת STATUS.md.
זה מה שניסיתי לעשות: ___
זו ההודעה/התקלה שקיבלתי (הדבק במלואה): ___
תסביר לי מה קרה במילים פשוטות, ואז תקן.
```

## <a name="p4"></a>P4 · סטייה/שינוי מהתוכנית באמצע מודול
🕐 כשרוצים לשנות משהו שכבר סוכם בבלופרינט של המודול הפעיל (מסך, שדה, התנהגות).
```
אני [ישי/עמית]. אני רוצה לשנות משהו מהתוכנית המאושרת של המודול הפעיל.
מה אני רוצה לשנות ולמה: ___
קרא את docs/micro_guides/module-N.md של המודול הפעיל (לפי STATUS.md) ואת CLAUDE.md.
לפני ביצוע: הסבר לי מה המשמעות — מה מושפע (מסכים, בדיקות, DB, מודולים אחרים) — וקבל את אישורי.
אחרי ביצוע: עדכן את יומן הסטיות במדריך המיקרו (הערת ↳ as-built, כלל ברזל 15),
עדכן את הבדיקות בהתאם לשינוי, ואם נדרשת הכרעה עסקית פתוחה — רשום ב-PROJECT_MASTER §7 ואל תכריע לבד.
בסוף: כל האדוות לפי כלל ברזל 13 + יומנים לפי פרוטוקול סוף-סשן.
```

## <a name="p5"></a>P5 · ‏merge conflict
🕐 כש-git עוצר עם conflict (במשיכה, במיזוג, ב-PR).
```
אני [ישי/עמית]. יש לי merge conflict ב-git ואני לא בטוח מה לעשות.
הפקודה שהרצתי: ___
מה git הציג (הדבק במלואו): ___
תסביר לי בעברית פשוטה: מה מתנגש עם מה, ומה כל צד של הקונפליקט אומר.
הצע פתרון והסבר למה דווקא הוא — אל תבצע לפני שאישרתי.
אסור בשום מצב: git push --force, או מחיקת עבודה של המפתח השני.
אחרי הפתרון: הרץ npm run verify והראה לי שהכל ירוק.
```

## <a name="p6"></a>P6 · שחזור / ביטול שינוי (undo)
🕐 כש-Claude עשה משהו לא צפוי, או שהתחרטתם על שינוי.
```
אני [ישי/עמית]. בוצע שינוי שאני רוצה לבטל.
מה קרה / מה אני רוצה לבטל: ___
לפני הכל: הרץ git status ו-git diff, והסבר לי בעברית פשוטה מה בדיוק השתנה ומה יימחק אם נשחזר.
אל תשחזר שום דבר לפני שאישרתי במפורש אילו קבצים.
אם השינוי כבר בקומיט — הסבר לי את האפשרויות (למשל revert) ואל תשכתב היסטוריה שכבר נדחפה.
```

## <a name="p7"></a>P7 · רגרסיה אחרי משיכת עבודה של השני
🕐 אחרי `git pull` שהביא שינויים של המפתח השני (למשל אחרי merge של מודול שלו).
```
אני [ישי/עמית]. הרגע משכתי שינויים של המפתח השני ואני רוצה לוודא שהצד שלי עדיין עובד.
קרא את STATUS.md ואת השורות החדשות ב-docs/CHANGELOG.md (מה נכנס).
הרץ npm run verify ואת npm run test:e2e, ובדוק את נקודות ההשקה:
הרשאות/RLS (מודל האבטחה, כלל ברזל 9), ניווט/סייד-בר, וכל טבלת DB משותפת שהשתנתה.
דווח לי בעברית: מה ירוק, מה נשבר (אם משהו), ומה ההשפעה על המודול שבעבודה אצלי.
אל תתקן קוד של המפתח השני בלי לתאם — רק דווח.
```

## <a name="p8"></a>P8 · שיחת קריאה-בלבד במקביל לסשן כותב
🕐 כשרוצים לשאול/לתכנן בזמן ששיחה אחרת בונה (כלל ברזל 16 — מותר, בקריאה בלבד).
```
אני [ישי/עמית]. תקרא בלבד — יש כרגע סשן Claude אחר שכותב (כלל ברזל 16).
אל תערוך, אל תיצור ואל תמחק שום קובץ, ואל תריץ פקודות שמשנות משהו —
עד שאגיד לך במפורש שהסשן השני סיים.
השאלה/המשימה שלי: ___
```

## <a name="p9"></a>P9 · "עשיתי ידנית" — פעולה מחוץ ל-Claude
🕐 אחרי פעולה ידנית ב-Supabase Studio / GitHub / מקום אחר, שהתיעוד לא יודע עליה.
```
אני [ישי/עמית]. ביצעתי פעולה ידנית מחוץ ל-Claude והתיעוד לא משקף אותה.
מה עשיתי (איפה ומה בדיוק): ___
אמת את המצב בפועל (Supabase MCP למצב DB / git / קריאת קבצים — לפי העניין),
ועדכן את התיעוד שישקף: CHANGELOG (אם DB/קוד), CLAUDE_CODE_LOG, STATUS.md — לפי חלוקת האחריות ב-CLAUDE.md.
אם הפעולה הידנית סותרת משהו בתיעוד או בתוכנית — סמן את הסתירה ושאל אותי; אל תיישב אותה לבד.
```

## <a name="p10"></a>P10 · שאלה פתוחה חדשה → רישום ב-§7
🕐 כשצצה שאלה עסקית/ארכיטקטונית שדורשת הכרעה — במקום שתלך לאיבוד או שקלוד יכריע לבד.
```
אני [ישי/עמית]. עלתה שאלה פתוחה חדשה שדורשת הכרעה.
השאלה: ___
ההקשר (איזה מודול/מסך/צעד נתקע בגללה): ___
רשום אותה ב-docs/PROJECT_MASTER.md §7 לפי הפורמט הקיים (מספר עוקב, רקע, סטטוס "פתוח — להכרעה משותפת עם ישי").
אל תכריע ואל תממש פתרון — רק רשום, ציין אילו צעדים חסומים עד ההכרעה, ועדכן STATUS.md אם זה חוסם.
```

## <a name="p11"></a>P11 · "הסבר לי" — למידה
🕐 כשרוצים להבין מה נבנה ולמה — בלי לשנות כלום.
```
אני [ישי/עמית]. אני רוצה להבין, לא לשנות.
מה להסביר (קובץ/פונקציה/החלטה/מסך): ___
קרא את מה שצריך והסבר לי כמו למתחיל: מה זה עושה, למה זה בנוי דווקא ככה, ואיך זה מתחבר לשאר המערכת.
אל תערוך שום קובץ בשיחה הזאת — אם תמצא בעיה תוך כדי, רק ציין אותה בסוף.
```
