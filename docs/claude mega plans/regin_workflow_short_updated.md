### הכרעה מראש #4 — שלוש שורות ל-`_shared/discipline.md`

**זו שימור, לא חקיקה חדשה.** שלוש השורות האלה קיימות היום בתוך `work-manager`
ויהפכו לבלתי-נגישות ברגע שהוא יארכב. הן מרחיבות את טבלת-האימות **שכבר קיימת**
בקובץ ("איזו טענה מאומתת איפה"), ואינן כלל חדש.

**הקובץ כתוב באנגלית — הוסף באנגלית, מתחת לטבלה הקיימת:**

- **An absence-claim is verified the way the SOURCE writes it, not the way the
  reporter searched.** *(Bit twice: "§7.86 missing" was grepped as `7.86` while the
  registry writes `86.`; and a Hebrew grep run over an English-language corpus.)*
- **Never hand a checker an expected number — only a measurement method.**
  *"Run it and report the count"*, never *"there should be 71"*. An expected number
  bends a checker toward confirmation instead of measurement.
- **A fix is not done until you have checked where else the same defect lives.**
  *(Three occurrences in two days: a rule landed in one file while the artifact the
  worker actually reads stayed stale.)*

**ובנוסף — שורה רביעית, והיא נכנסת לטבלה הקיימת ולא לרשימה.**
בקובץ יש טבלת *"Claim | Where to check, in THIS repo"* עם ארבע שורות
(‏§7 · "כבר בוצע" · "מוזג" · "עמודה/מדיניות קיימת"). **חסרה בה בדיוק סוג-הטענה
שכבר הפיל אותנו בפועל.** הוסף שורה חמישית לטבלה:

```markdown
| "it works" / "the tests are green" / "this is what the screen looks like" | run it through the **production path** — `npm run test:e2e`, the real browser, the served asset — and **say which path produced the artifact you are judging**. *(Anchor `ba2d41e`: the quote PDF was defective in its **production**, not in its code — it had been rendered under vitest instead of fetched from the browser blob, so the verification method lied while the code was fine. A green result from the wrong path is not a green result.)* |
```

🔴 **חשוב שזו שורת-טבלה ולא בולט:** הטבלה היא המנגנון שאומר "איזו טענה מאומתת איפה",
ובולט מתחתיה נקרא כהערה. **אם השורה לא נכנסת לטבלה — היא לא נכנסה.**

🚫 **אל תוסיף שום שורה אחרת לקובץ הזה, ואל תוסיף דבר ל-`CLAUDE.md`** —
הוא נגזם בכוונה ב-28/07 מ-17 כללים ל-7, ואין להפוך את ההכרעה הזו.

`module-close` הוא שער הסגירה העצמאי האחרון לפני מיזוג.

## מקורות אמת

עדכן את ה-Skill כך שסדר מקורות האמת יהיה:

3. micro-guide מאושר ו-as-built — תוכנית הבנייה, DoD,
   QA matrix, החלטות טכניות וראיות.
4. דוחות quality-audit, quality-fix ובדיקת-החזרה —

מפרטים ישנים, step guides ומסמכים היסטוריים הם הקשר בלבד.

להשתמש רק אחרי סגירת מודול 4, לפני הרחבת השיטה למודולים אחרים.

```text
מודול 4 נסגר. בדוק האם שיטת העבודה החדשה באמת עזרה לי.

אל תציע שינוי חדש לפני הסיכום.

החזר טבלה קצרה:
מדד | מה קרה בפועל | ראיה או דוגמה | פסק דין
- האם היה ברור לי מה Claude צריך ממני ולמה
- האם קיבלתי רק שאלות מוצר, תהליך, הרשאות או UX
- האם הנחות ופערים התגלו לפני Blueprint או קוד
- האם Claude התקדם לבד בפרטים טכניים הפיכים
- האם נוצר מסמך או שער שלא נתן ערך
- האם גילינו תיקון מאוחר שהיה אפשר למנוע
- האם האפיון והמוקאפים המאושרים עזרו בבדיקה ובסגירה
- האם נותרה תלות ב-work-manager או במסלול הישן

אחר כך המלצה אחת בלבד:
- להשאיר כפי שהוא
- לפשט
- לתקן ולנסות שוב במודול הבא
- לבטל חלק מסוים

הבחן בין ראיה, ההתרשמות שלי והמלצה שלך.
אל תעדכן Skills בלי אישור מפורש שלי.
```

# מסנן לפני הוספת כלל או Skill

```text
עלה רעיון להוסיף כלל, Skill, Hook, מסמך או שער חדש:
[תאר את האירוע או הרעיון]

לפני שמוסיפים משהו, בדוק:
1. האם זו בעיה מוכחת, דפוס שחזר, או אירוע חד-פעמי.
2. האם כלל, Skill או בדיקה קיימים כבר מטפלים בה.
3. האם אפשר לתקן מקומית או לפשט כלל קיים.
4. אם מוסיפים משהו, מה הוא מחליף או מסיר.
5. מה הטריגר המדויק שלו, מי משתמש בפלט, ומה העלות בכל מודול.
6. איך נדע בניסוי אמיתי שהוא עזר.

בחר המלצה אחת בלבד:
- לא עושים דבר כרגע ומתעדים
- מתקנים מקומית
- מחזקים כלל קיים
- מחליפים כלל קיים
- יוצרים רכיב חדש

אל תיצור שכבה חדשה רק כי האירוע מפחיד.
עצור וחכה להחלטה שלי.
```
