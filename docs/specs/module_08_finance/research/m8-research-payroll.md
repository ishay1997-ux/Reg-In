Scope note: REG-IN is an academic-project events company — one finance manager, no ops team, ~50 hostesses paid hourly, 2-5 per event, no real end-users. Every finding below is filtered for that scale, not for a payroll bureau's own internal audit needs.

## Q1 — Typical flow: cutoff day, format (Excel vs portal), expected columns for hourly workers

**The outsourced-bureau flow itself is well documented and generic across many Israeli CPA/bookkeeping sites** (bscpa.co.il, yael-sachar.com — both describe the same 3-step model):
1. **Employer collects and sends "variable data"** (נתונים משתנים) to the bureau: hours worked, absences, sick days, vacation days, overtime, pension deductions, expense reimbursements, other benefits.
2. **Bureau calculates**: tax withholding, Bituach Leumi (National Insurance), and all statutory deductions/additions.
3. **Bureau produces payslips** (digital or physical) and returns them to the employer/employees.
Source: [הפקת תלושי שכר במיקור חוץ — bscpa.co.il](https://bscpa.co.il/%D7%A2%D7%AA-%D7%A8%D7%A6%D7%95%D7%9F-%D7%91%D7%A2%D7%9E/%D7%94%D7%A4%D7%A7%D7%AA-%D7%AA%D7%9C%D7%95%D7%A9%D7%99-%D7%A9%D7%9B%D7%A8-%D7%91%D7%9E%D7%99%D7%A7%D7%95%D7%A8-%D7%97%D7%95%D7%A5/), [הפקת תלושי שכר באמצעות חשבים נט — yael-sachar.com](https://www.yael-sachar.com/%D7%94%D7%A4%D7%A7%D7%AA-%D7%AA%D7%9C%D7%95%D7%A9%D7%99-%D7%A9%D7%9B%D7%A8-%D7%A2%D7%9D-%D7%97%D7%A9%D7%91%D7%99%D7%9D-%D7%A0%D7%98/)

**Cutoff day-of-month**: I did not find a source stating a universal cutoff day bureaus impose on employers (this varies bureau-to-bureau and is set by private agreement, not law). What IS legally grounded: the **legal payment deadline** — wages must be paid by the 9th day after the end of the month worked; if a variable-pay report/component depends on an employee submission, and that submission arrives **at least 5 days before month-end**, it must be paid with that month's cycle (by the 6th of the next month); if submitted later, it rolls to the **following month's** payroll cycle. Source: [מועד תשלום השכר — Kolzchut](https://www.kolzchut.org.il/he/%D7%9E%D7%95%D7%A2%D7%93_%D7%AA%D7%A9%D7%9C%D7%95%D7%9D_%D7%94%D7%A9%D7%9B%D7%A8), general-search synthesis (see search transcript) citing Wage Protection Law regulations.
**Fit**: this "5-days-before-month-end / else rolls to next month" rule is a strong, directly-usable anchor for a REG-IN cutoff day (e.g. hours must be finalized by the 25th to make that month's report) — grounded in labor law, not invented. **Flagged as recommendation basis, not yet Ishay's ruling.**

**Format — Excel vs bureau portal**: I found **no authoritative source comparing bureau preference for xlsx vs a bureau's own portal** for a 5-10-employee company; searches returned only generic CPA-pricing pages and Excel-tutorial content, not documented bureau intake preferences. **Searched and not found — tag as gap.** What the outsourcing-flow pages *do* establish (see above) is that the employer is the one compiling and transmitting "variable data" monthly — consistent with a small company just emailing a spreadsheet rather than using the bureau's own software, since Malam/other big bureaus' own portals (Malam Payroll Plus) are aimed at larger organizational HR/attendance-system integration, not appropriate for a 1-person finance operation. Source: [Malam Payroll Plus](https://www.malam-payroll.com/) (own positioning: enterprise HR/attendance/pension systems).
**Fit**: for REG-IN's scale (one finance person, ~50 hourly hostesses), a plain exported file (Excel or PDF) sent by email/portal-upload is the world-standard pattern for micro-businesses; a dedicated bureau-portal integration is a solution to a scale problem REG-IN doesn't have.

**Expected columns for hourly workers**: **No source gave a canonical "the accountant expects exactly these columns" list.** Generic Excel-hours-template blogs (excelwiz.co.il, excelent.co.il, meckano.co.il) converge on a common but non-authoritative column set for hour-tracking sheets: employee identifier, name, date, day-of-week, clock-in/out, total hours, overtime hours, hourly rate, absence/shortfall flags, amount to pay. None of these are payroll-bureau-authored sources — they are Excel-tutorial sites. **Tag: מהידע שלי (עולמי, לא ישראלי-ספציפי), לא אומת מפי משרד שכר בפועל** — ת"ז/employee ID, hours, rate, bonuses, travel are the intuitively necessary fields but no bureau published a checklist confirming it.
**Fit**: given REG-IN already computes gross profit and salary data per event, the "expected columns" question likely already has a definitive local answer in `docs/schema.sql` / the payroll module's actual data model — that beats an unverified world guess. Recommend cross-checking against REG-IN's own hostess/event tables rather than importing a generic template.

## Q2 — Month attribution: work-month vs report-month; late-finalized hours

**Attribution rule (grounded)**: Israeli payroll practice ties wages to the **month the work occurred**, not the month it happens to be reported/paid — this is implicit in the wage-protection payment-deadline rule itself (wages for month X must be paid by the 9th of month X+1) and explicit in the "variable component" rule above (a late-arriving report for month X's work still gets attributed to X's cycle if submitted in time, or rolls to X+1 if not — the work-month identity does not change, only which pay-run it lands in). Source: [מועד תשלום השכר — Kolzchut](https://www.kolzchut.org.il/he/%D7%9E%D7%95%D7%A2%D7%93_%D7%AA%D7%A9%D7%9C%D7%95%D7%9D_%D7%94%D7%A9%D7%9B%D7%A8).

**Late-finalized hours — corrected via retro line in the NEXT report, not an amended report**: A regulatory clarification from the Ministry of Economy (משרד הכלכלה), surfaced in search, states that a **subsequent-month reconciliation of variable components** for the prior month's regular hours, done in the month **after** the payslip was already issued, is **standard/acceptable practice** (נוהל תקין) — i.e., the normal fix is a retroactive correction line folded into next month's report, not re-issuing/amending the original payslip. Also: overtime specifically may lawfully be paid **at the start of the following month** under Wage Protection Regulations even under normal (non-late) conditions. Sources: search-result synthesis citing משרד הכלכלה guidance (see WebSearch transcript for "שכר רטרואקטיבי דיווח חודש עבודה") and general Wage Protection Regulations context; **exact regulation number/official document was not independently fetched — flag for a follow-up direct citation if this becomes a ruling basis**.
**Fit**: this directly validates a "retro line in next month's report" model over "amend the sent report" — matches how a `salary_reports` append-only/signing model would naturally work, and avoids ever needing to un-sign or reopen a closed report. **Strong fit, cheap to implement, no scale mismatch.**

## Q3 — החזר הוצאות נסיעה 2025/2026: mandatory status, cap, per-shift vs per-km, separate line or folded in

**Still mandatory (צו הרחבה) — confirmed, economy-wide.** The obligation is anchored in a general צו הרחבה covering the whole economy: the employer must reimburse commuting cost to/from work for every workday the employee needs transport, if the employee lives ≥500m from the workplace (or otherwise needs transport). Sources: [החזר הוצאות נסיעה — Kolzchut](https://www.kolzchut.org.il/he/%D7%94%D7%97%D7%96%D7%A8_%D7%94%D7%95%D7%A6%D7%90%D7%95%D7%AA_%D7%A0%D7%A1%D7%99%D7%A2%D7%94), [דמי נסיעות — bizportal.co.il](https://www.bizportal.co.il/career/news/article/20035635), [הוצאות נסיעה 2026 — metaintro.com](https://www.metaintro.com/he/blog/travel-expenses-israeli-labor-law-2026).

**Current daily cap: ₪22.60/workday (2025/2026 figure, converged across 3 independent sources)** — Kolzchut, kolhamas.co.il, aloncohen-law.co.il, lawlioz.com all state the same figure. The employer pays the **lower of**: actual cheapest public-transit round-trip cost, or the ₪22.60 daily ceiling (or the monthly-pass price if that's cheaper than daily fares × workdays). Sources as above.

**Per-shift (daily), not per-km, for ordinary commuting.** The reimbursement is explicitly a **per-workday** amount tied to public-transit cost, not a distance/km rate — km rates (₪2.54/km up to 2,500km, ₪1.58/km above, for 2026) apply to a **different** category: travel *for* work (client visits, errands) with a private vehicle, not commuting to a fixed workplace. Source: WebFetch of Kolzchut travel-reimbursement page; km-rate figures from WebSearch synthesis (see "דמי נסיעה עובדים במשמרות" query — km rates not independently re-verified from a primary source in this pass, tag as **medium confidence**).
**Special note directly relevant to hostesses working events**: the WebFetch summary of Kolzchut states that employees with **split shifts** (worked example given: "event venue staff") receive **double the reimbursement or the monthly-pass equivalent** — i.e. if a hostess works two separate call-times in one day requiring two separate round trips, that is explicitly contemplated as a recognized case, not an edge case invented for this project. **This is a directly-usable anchor**, but confirm the "קורה אצלך" reality check with Ishay before building for it (do hostesses ever do 2 separate shifts/call-times in the same calendar day at REG-IN today?).

**Must be a separate line for the accountant — folding it into gross wage carries real risk.** A dedicated source states plainly: if travel reimbursement is folded into a general/global wage without the employee's **explicit written consent**, then severance pay and other social/statutory entitlements will be calculated **only** off the wage line, silently excluding the travel component from that base — an outcome most employers do not intend. The recommended and clean practice is a **separate "החזר הוצאות נסיעה" line item on the payslip**, distinct from base wage. Source: [הכללת דמי נסיעות ודמי חגים בתוך שכר שעתי — ovdim.org.il](https://www.ovdim.org.il/%D7%A9%D7%9B%D7%A8-%D7%A9%D7%A2%D7%AA%D7%99-%D7%9B%D7%95%D7%9C%D7%9C-%D7%A0%D7%A1%D7%99%D7%A2%D7%95%D7%AA-%D7%97%D7%92%D7%99%D7%9D/) plus corroborating context from [מבנה תלוש השכר — ay-labourlaw.co.il](https://www.ay-labourlaw.co.il/%D7%9E%D7%91%D7%A0%D7%94-%D7%AA%D7%9C%D7%95%D7%A9-%D7%94%D7%A9%D7%9B%D7%A8/).
**Fit**: strong, low-cost, high-consequence — if REG-IN's payroll-summary export currently blends travel into a single "gross pay" number per hostess, that is a **practice mismatch worth flagging to Ishay**, not a nice-to-have. This is exactly the kind of "world convention that solves a real local problem" the CLAUDE.md external-anchor rule asks for.

## Q4 — Duplicate-payment prevention: is a report-run register a recognized practice?

**No Israel-specific source found describing a "report-run register" as a named, recognized small-business practice.** Searches for בקרת שכר / מניעת כפל תשלום / התאמה בין חודשים returned only generic Excel-tutorial content, not documented control procedures from Israeli bureaus or accounting bodies. **Searched and not found.**

**What general (non-Israel-specific) payroll-reconciliation literature does establish, converged across multiple sources (Justworks, QuickBooks, Fit Small Business, PeopleManagingPeople, APS Payroll, Deel):**
- **Segregation/approval-then-lock is the recognized pattern**: hours get approved once, then feed the pay run; "approved" and "paid" are tracked as two distinct states so a later process can verify a run actually paid what was approved.
- **"Avoid silent edits"** is called out explicitly: if hours can be changed after approval with no record of who/why/when, the record can't be trusted or defended later — the correct pattern is to **document any correction and re-run approval**, not silently overwrite.
- Reconciliation is done as a recurring end-of-period discipline (matching what was approved against what was actually disbursed), not as a one-off spot-check.
Sources: [Justworks — Payroll Reconciliation Strategies](https://www.justworks.com/blog/payroll-reconciliation-strategies-that-actually-work), [QuickBooks — Payroll Reconciliation](https://quickbooks.intuit.com/r/payroll/payroll-reconciliation/), [Fit Small Business — Payroll Reconciliation](https://fitsmallbusiness.com/how-to-do-payroll-reconciliation/).

**Fit assessment**: REG-IN's existing `salary_reports` **signing/lock model** (referenced in the task's framing — a report, once generated/signed, becomes immutable) is a **direct structural match** to the "approve-then-lock, no silent edits, corrections are new documented entries" pattern found in the general literature — this is the practice to import, and REG-IN already independently arrived at its shape (per the eb17b19 migration commit in recent git history: "phase 1 — four migrations applied"). The literature doesn't hand REG-IN a new mechanism so much as **validate the one already chosen**: don't let it be edited in place; a correction is a new signed entry (ties directly to Q2's "retro line" finding). No world source suggests anything more elaborate (e.g. a full audit-log system, multi-approver workflow) is standard at this scale — that would be importing a solution to a multi-approver/fraud-prevention problem REG-IN's single-finance-person structure doesn't have.

## Q5 — Does the payroll file need a timestamp/total-row/immutable copy? Do bureaus prefer xlsx?

**No Israel-specific, bureau-authored source found stating these as requirements.** Searches for "קובץ אקסל לרואה חשבון שורת סה"כ תאריך הפקה" and the xlsx-preference question returned only generic accounting-software marketing pages (EasyCount, iCount, invoice4u, Chashbashevet/BKMV export-format docs) — none of which document a bureau's actual intake checklist for a payroll-hours file specifically. **Searched and not found — flag as a real gap, not filled by inference.**

**What is defensible from adjacent evidence:**
- General accounting-file norms in the Israeli software ecosystem do favor **总 (total) rows and file-level metadata (producing software + date/time stamp)** as a documented convention for financial exports intended for a third party — this shows up in unified-file-export documentation (Chashbashevet's BKMV standard) but that is a **statutory unified-file format for a different purpose (tax authority audit files)**, not evidence for a monthly hours-summary sent informally to a bureau. **Tag: analogic inference, not a direct citation — mark as מהידע שלי, לא אומת ישירות.**
- xlsx as the default exchange format for small-business-to-bureau hour reports is consistent with the outsourcing-flow sources in Q1 (bureaus receive "variable data" from the employer, and Excel is the near-universal default business tool for this in Israel) but again **no source states bureaus prefer xlsx over PDF/CSV/portal-entry specifically**.

**Fit assessment**: given REG-IN already treats a signed salary report as immutable once generated (Q4), an xlsx export **with a total row and a generation timestamp already embedded in the file** is a low-cost, defensible default that satisfies the *spirit* of what the (thin) evidence suggests without needing a fabricated "bureaus require this" claim. Recommend presenting this to Ishay as **a sensible default, not a proven requirement** — the accountant's actual preference is a "קורה אצלך" question only Ishay/the CPA relationship can answer definitively, since no external convention was found strong enough to override a direct check.

## Considered and Rejected for This Project

| World practice found | Why rejected here |
|---|---|
| Large-bureau portal integration (Malam Payroll Plus-style attendance/HR-system sync) | Solves an integration problem for orgs with dedicated HR/attendance software and many employees; REG-IN has one finance person and a spreadsheet-scale hours volume — a portal integration is scale infrastructure for a scale problem that doesn't exist here. |
| Multi-approver payroll sign-off workflow (separate preparer + approver roles, "divide responsibilities among staff to prevent fraud" — from Justworks/Deel literature) | Explicitly a fraud/segregation-of-duties control for organizations with more than one person touching payroll. REG-IN has a single finance manager; there is no second person to segregate duties from. Importing this would be building an audit-trail control for a multi-actor threat model REG-IN doesn't have. |
| Formal audit-log / full change-history system for payroll data | General reconciliation literature mentions avoiding "silent edits," which REG-IN's existing signed/locked report model already satisfies structurally. A dedicated audit-log subsystem beyond that (who-viewed-what, IP logging, etc.) would be solving a regulatory/compliance-audit problem this academic project does not have (no real external audit, no real regulator). |
| Unified statutory export file formats (e.g. BKMV / מבנה אחיד) for accounting software interchange | This is a formal, regulator-defined format for exchanging *general ledger/accounting* data between systems (e.g. for tax-authority audits), not for an informal monthly hours-summary sent to a CPA. Importing its rigor (fixed record layout, checksums) would solve a system-interoperability problem REG-IN — sending a human-readable Excel to one specific accountant by email — does not have. |
| Km-based mileage reimbursement model for ordinary commuting | This category (₪2.54/₪1.58 per km) applies to travel *for* work using a private vehicle (client visits etc.), not to commuting to a fixed event/office location — importing it for hostess commute-to-event reimbursement would misapply a different legal category to a case (fixed-location daily commute) that the flat daily-cap rule already covers correctly. |

## Digest (for the orchestrating session)

1. **Outsourced-bureau flow is well-documented and generic**: employer sends "variable data" (hours/absences/overtime/etc.) monthly → bureau computes deductions → bureau issues payslips. No canonical column list or bureau-stated cutoff day was found anywhere — those are gaps, not findings.
2. **Legally-grounded cutoff anchor exists even though no bureau-specific one does**: a variable component reported ≥5 days before month-end is paid in that month's cycle; later, it rolls to next month. Usable as REG-IN's cutoff logic basis.
3. **Month attribution = work-month, always.** Late-finalized hours get a **retroactive correction line in the next report**, not an amended/reopened original — Ministry-of-Economy guidance (found via synthesis, not primary doc) calls this standard practice. This directly supports an append-only `salary_reports` model.
4. **Travel reimbursement (נסיעות) is still mandatory, ₪22.60/workday cap (2025/2026, 3 independent sources agree)**, paid per-workday not per-km for ordinary commuting, and **must appear as its own payslip line** — folding it into gross wage without explicit written consent silently shrinks the severance/social-benefits calculation base. This is a real risk-carrying gap worth flagging to Ishay if REG-IN currently blends it into one number.
5. **Split-shift/double-callback workers are an explicitly recognized case for double travel reimbursement** in Israeli practice (not a REG-IN-invented edge case) — but confirm with Ishay whether hostesses ever actually work two separate call-times in one day before building for it.
6. **No Israel-specific "report-run register" practice found.** General (non-Israeli) payroll-reconciliation literature converges on "approve-then-lock, no silent edits, corrections are new documented entries" — which is a structural match to REG-IN's existing signed/immutable `salary_reports` model already in migrations (validates the existing design rather than adding a new one).
7. **No source found for a bureau-stated xlsx preference, or a stated total-row/timestamp/immutable-copy requirement.** Both are defensible low-cost defaults by analogy, not proven requirements — present to Ishay as "reasonable default," not "world standard."
8. **Rejected-as-mismatched-to-scale**: bureau-portal integrations, multi-approver segregation-of-duties workflows, formal audit-log systems, statutory unified accounting-export formats (BKMV), and km-based mileage for ordinary commuting — each solves a scale/multi-actor/regulatory-audit problem REG-IN does not have.

Full findings, sources, and the reject-list rationale are in the file above (by question). Six explicit "searched, not found" gaps are listed — worth surfacing to Ishay as open items rather than filled with invented specifics.
