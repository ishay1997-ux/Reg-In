# – ניתוח המערכת <a id="sec-2"></a> <!-- מקור C6 L3 -->

## 2.1 שיטת הניתוח הנבחרת <a id="sec-2-1"></a> <!-- מקור C6 L4 -->

תרשים זרימת נתונים (DFD - Data Flow Diagram) הוא כלי גרפי המאפשר לתאר את זרימת המידע בין תהליכים, מאגרי נתונים וגורמים חיצוניים. לצורך ניתוח מערכת REG-IN נבחרה שיטה זו בהתאם למתודולוגיית ADISSA של פרופ' פרץ שובל. הניתוח מוצג בשלוש רמות פירוט: תרשים הקשר (רמה 0), תרשים הפונקציות הראשיות (רמה 1), ותרשימי הפירוק לפונקציית משנה (רמה 2).

## 2.2 מילון רכיבי המערכת – DFD <a id="sec-2-2"></a> <!-- מקור C6 L6 -->

**ישויות חיצוניות (U):**

| מזהה | ישות | תיאור ותפקיד במערכת |
|---|---|---|
| U1 | לקוח | בקשה ואישור הצעת מחיר, קבלת חשבונית מס. |
| U2 | דיילת (עובדת שטח) | קבלת זימוני משמרת במייל ומענה באמצעות קישור. |
| U3 | מנהלת כספים ולקוחות | ניהול לקוחות, גבייה, הפקת חשבוניות, דוחות שכר והזנת משובים. |
| U4 | מנהלת פרויקטים | הפקת הצעות, הקמת פרויקטים, עדכון שעות ונתוני ביצוע, קבלת התראות מערכת. |
| U5 | מנהלת גיוס | הפעלת Smart Match, בחירת דיילות, שליחת זימונים ואישור שיבוצים סופיים. |
| U6 | מנהלת לוגיסטיקה | ניהול הזמנות מוצרים לאירוע ועדכון סטטוס פריטים לוגיסטיים במערכת. |
| U7 | מנהל מערכת (מנכ"ל) | ניהול משתמשים, הגדרת הרשאות, עדכון פרמטרים גלובליים ותעריפים. |
| U8 | משרד רואה חשבון | קבלת דוח שעות חודשי במייל. |

**ישויות זמן / טריגרים (T):**

| מזהה | טריגר | תדירות / לוגיקה |
|---|---|---|
| T1 | פקיעת תאריך אירוע | יומי; שינוי אוטומטי של סטטוס הפרויקט ל-"אירוע הסתיים". |
| T2 | פקיעת תוקף הצעת מחיר | יומי; העברת הצעה ללא מענה מעל 30 יום לסטטוס "נדחתה". |
| T3 | תזכורת מייל לדיילות | מתוזמן; שליחת מייל אוטומטי עם פרטי האירוע לדיילות שאושרו סופית. |

> 🔧 **פגם ידוע (§9 #13):** התיאור של T3 כאן ("שליחת מייל עם פרטי האירוע לדיילות שאושרו סופית") מתאר בפועל את פעולת **האישור-הסופי הידנית** (§5.8.6), ולא את **התזכורת-לפני-משמרת** (§5.8.7). המימוש: לפי §5.8.7 (פרמטר-שעות). הפרוזה נשארה מילה-במילה; ר' `db_roadmap.md` §9 + §7.42.

**מאגרי נתונים (D):**

| מזהה | מאגר נתונים | תכולת המאגר |
|---|---|---|
| D1 | מאגר לקוחות | פרטי לקוחות, אחוז הנחה קבועה, אישורי דיוור ומשובים היסטוריים. |
| D2 | מאגר דיילות | פרופיל דיילות, שכר שעתי, דירוג מקצועי, סטטוס ופרטי בנק. |
| D3 | קטלוג ומחירון | פריטי שירות ולוגיסטיקה, מחירי בסיס, עלות רכש ומדרגות מחיר לפי כמות. |
| D4 | מאגר הצעות מחיר | הצעות שהופקו, שירותים כלולים, הנחות, סטטוס ההצעה וקישור לקובץ PDF. |
| D5 | מאגר פרויקטים | נתוני אירועים, סטטוס פרויקט, נתוני ביצוע בפועל ומשובים. |
| D6 | מאגר שיבוצים | קשרי העסקה (פרויקט-דיילת), סטטוס שיבוץ, שעות בפועל ובונוסים. |
| D7 | מאגר דוחות שכר | רשומות ריכוז שכר חודשי ותאריך שליחה לרו"ח (למניעת כפילויות). |
| D8 | משתמשים והרשאות | נתוני עובדי מטה, סיסמאות מוצפנות, תפקידים, רמות הרשאה וסטטוס. |
| D9 | פרמטרי מערכת | משקולות אלגוריתם התאמה, שכר מינימום, תעריפים, מע"מ ותבניות מייל. |

**פונקציות מערכת ראשיות (F):**

| מזהה | פונקציה | תיאור הפעילות |
|---|---|---|

| F2 | נהל פרויקט ולוגיסטיקה | פתיחת פרויקט מהצעה מאושרת, ניהול הכנות מוצרים ושליחת התראות. |
| F3 | שבץ דיילות | סינון ב-Smart Match, שליחת זימונים, קליטת מענה ונעילת שיבוצים. |
| F4 | בצע סגירה פיננסית | קליטת נתוני ביצוע, הפקת חשבוניות ודוחות, שמירת משובים. |
| F5 | נהל הגדרות והרשאות | ניהול משתמשים ותפקידים, הגדרת הרשאות גישה למודולים ועדכון פרמטרים. |

| מזהה פרויקט + מק"ט + מספר סידורי | מספרי שלם + אלפאנומרי + מספרי שלם | מפתח ראשי משולב (PK) | מספר סידורי = מפתח חלקי |
| מזהה פרויקט | מספרי שלם | מפתח זר (FK) ← טבלת פרויקטים | אילוץ ON DELETE CASCADE |
| מק"ט | אלפאנומרי | מפתח זר (FK) ← טבלת מוצרים | אילוץ ON DELETE RESTRICT |
| כמות מתוכננת | מספרי שלם | חובה | גדול מ-0 |
| כמות בפועל | מספרי שלם | חובה | ≥ 0 |
| סטטוס פריט | טקסט | חובה | [טרם החל \| הוזמן \| מוכן] \| ברירת מחדל: טרם החל |
| הערות לוגיסטיקה | טקסט חופשי | רשות |  |

תיאור: טבלת קשר תלויה המנהלת ניפוק ומעקב הזמנות מוצרים לכל פרויקט, עם מעקב סטטוס פרטני לכל פריט (Checklist). טבלת קישור M:N בין פרויקטים למוצרים.

> 🔧 **פגם ידוע (§9 #2):** "טבלת קישור M:N" — למעשה **ישות-קישור** הנושאת כמות-בפועל, סטטוס-פריט ומחיר. ר' §2.4.11 + `db_roadmap.md` §9 #2.

תכונות נגזרות (מחושבות בזמן אמת, אינן נשמרות פיזית): סך מחיר בפועל (מחושב אוטומטית ככמות × מחיר ליחידה).

מטרה עסקית: החלפת מעקב האקסל הידני ב-Checklist חכם: כאשר 100% מהפריטים בסטטוס "מוכן" - המערכת מקדמת אוטומטית את סטטוס הפרויקט.

### 2.4.14 טבלה – Assignments שיבוצי דיילות <a id="sec-2-4-14"></a> <!-- מקור C6 L364 -->

תיאור: טבלת קשר תלויה מרכזית המתעדת את קשרי ההעסקה בין פרויקטים לדיילות, כולל סטטוס שיבוץ, שעות ביצוע ושכר (טבלת קישור M:N בין פרויקטים לדיילות).

> 🔧 **פגם ידוע (§9 #2):** "טבלת קישור M:N" — למעשה **ישות-קישור** הנושאת שכר-מוקפא, שעות-בפועל, סטטוס-שיבוץ ובונוס. ר' §2.4.11 + `db_roadmap.md` §9 #2.

| שם השדה | סוג נתון | מפתח / אילוץ | תחום ערכים / הערות |
|---|---|---|---|
| מזהה פרויקט + ת"ז + מספר שיבוץ | מספרי שלם + אלפאנומרי + מספרי שלם | מפתח ראשי משולב (PK) | מספר שיבוץ = מפתח חלקי |
| מזהה פרויקט | מספרי שלם | מפתח זר (FK) ← טבלת פרויקטים | אילוץ ON DELETE CASCADE |
| ת"ז | אלפאנומרי | מפתח זר (FK) ← טבלת דיילות | אילוץ ON DELETE RESTRICT |
| קוד הפקת דו"ח | מספרי שלם | מפתח זר (FK) ← טבלת דו"חות שכר | אילוץ ON DELETE RESTRICT |
| סטטוס שיבוץ | טקסט | חובה | [ממתינה למענה (נשלח זימון) \| אישרה זמינות \| סירבה/לא יכולה \| אושרה סופית \| שוחררה] \| ברירת מחדל: ממתינה למענה |
| שכר שעתי באירוע | מספרי עשרוני | חובה | מוקפא מכרטיס הדיילת |
| שעות בפועל | מספרי עשרוני | חובה | ≥ 0 \| ברירת מחדל: 0 |
| בונוס אישי | מספרי עשרוני | חובה | ≥ 0 \| ברירת מחדל: 0 |
| נשלחה תזכורת | בוליאני | חובה | [אמת \| שקר] \| ברירת מחדל: שקר |

תכונות נגזרות (מחושבות בזמן אמת, אינן נשמרות פיזית): ציון התאמה משוקלל (מחושב ע"י מנוע ה-Smart Match בעת תהליך השיבוץ).

מטרה עסקית: ניהול תהליך Smart Match מקצה לקצה: זימונים, אישורים, מניעת Double Booking ברמת שאילתה, ושימור נתוני שכר מוקפאים לדו"ח חודשי.

### 2.4.15 טבלה – Permissions הרשאות תפקיד <a id="sec-2-4-15"></a> <!-- מקור C6 L380 -->

תיאור: טבלת קשר תלויה המיישמת את מטריצת ההרשאות: מגדירה את רמת הגישה של כל תפקיד לכל מודול (טבלת קישור M:N בין תפקידים למודולים).

| שם השדה | סוג נתון | מפתח / אילוץ | תחום ערכים / הערות |
|---|---|---|---|
| קוד תפקיד + קוד מודול | מספרי שלם + מספרי שלם | מפתח ראשי משולב (PK) | מזהה ייחודי משולב |

## 2.5 סכמת בסיס הנתונים (הסכמה הרלציונית) <a id="sec-2-5"></a> <!-- מקור C6 L390 -->

הסכמות נוצרו על בסיס תהליך מיפוי של תרשים קשרי הגומלין (ERD) משלב הניתוח, תוך יישום כללי הנרמו למניעת יתירות נתונים ואנומליות בשליפה ובעדכון. במעבר למודל הלוגי הרלציוני, כל רלציה (טבלה) מייצגת ישות או קשר מובהק מהמודל יחסי הגומלין, כאשר תכונות מורכבות פורקו לשדות אטומיים ותכונות נגזרות הושמטו על מנת לשמור על מקור אמת יחיד. עבור כל רלציה הוגדר מפתח ראשי (מסומן בקו תחתון) המזהה כל רשומה באופן ייחודי, ומפתחות זרים (מסומנים בקו תחתון מקווקו) המקשרים בין הטבלאות השונות. מפתחות זרים אלו הם הבסיס לאכיפת אילוצי שלמות הייחוס.

## 3.3 תרשים ישויות קשרים <a id="sec-3-3"></a> <!-- מקור C6 L450 -->

תרשים ישויות קשרים הינו כלי המשמש לתיאור ולתכנון מבנה הנתונים הלוגי במערכת. התרשים מציג את הישויות המרכזיות במערכת ואת הקשרים ביניהן, ובכך מאפשר להבין כיצד הנתונים במערכת מקושרים זה לזה.
